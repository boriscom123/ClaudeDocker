# ClaudeDocker

Общий слой Docker для VPS: то, что нужно **более чем одному проекту**.

Правило владения одной строкой: ресурс нужен нескольким проектам — он описан
здесь; нужен одному — в репозитории этого проекта.

## Что здесь

| Сервис | Версия | Роль |
|---|---|---|
| `nginx` | 1.31.4-alpine | единственная точка входа сервера: `:80`, `:443`, TLS, ACME |
| `postgres` | PostGIS 18-3.6 | общая база — её используют `game` и `uzbek_queue` |
| `redis` | 8.10-alpine | общий кеш и очереди |
| `portainer` | latest | просмотр контейнеров, только на loopback |

Версии закреплены явно, включая `nginx`: плавающий тег делает сборку
невоспроизводимой. Node в проектах — 24 «Krypton», актуальный LTS.

```
docker-compose.yml                    общий слой
.env                                  НЕ в git: домены, бинды портов, пароли
nginx/templates/nginx.conf.template   каркас
nginx/templates/sites/*.template      по файлу на проект
projects/<имя>/docker-compose.yml     оверлей проекта под этот VPS
```

Репозиторий публичный, поэтому домены (в них входит адрес сервера), бинды
портов и пароли живут только в `.env`. В git уходит `.env.example`.

## Два вида compose

- **В репозитории проекта** — самодостаточный: проект поднимается на чистой
  машине со своей базой, своим кешем и своим веб-сервером. Всё, что на VPS даёт
  общий слой, объявлено под профилем `standalone`:
  `docker compose --profile standalone up -d`.
- **Здесь, в `projects/<имя>/`** — оверлей под этот VPS: снимает публикацию
  портов, подключает контейнеры к общим сетям. Профиль `standalone` не включается,
  поэтому дублирующие сервисы просто не создаются.

Проект подключает оверлей строкой в своём `.env`:

```
COMPOSE_FILE=docker-compose.yml:/home/boris/projects/ClaudeDocker/projects/<имя>/docker-compose.yml
```

## Запуск

```bash
docker network create web claude-net shared-data   # разово
docker compose up -d
```

## Как подключить новый проект

1. `nginx/templates/sites/<имя>.conf.template` — server-блоки 80 и 443,
   домен переменной `${<ИМЯ>_DOMAIN}`.
2. Переменная домена в `.env` и `.env.example`, плюс в `NGINX_ENVSUBST_FILTER`
   и в `environment` сервиса `nginx`.
3. `projects/<имя>/docker-compose.yml` — оверлей, если проекту нужны общие сети.
4. `COMPOSE_FILE` в `.env` проекта.
5. `docker compose up -d --force-recreate nginx` и проверить домен.

## Подводные камни, проверенные на практике

- **Апстримы резолвятся только внутри общих сетей.** `proxy_pass` на короткие
  имена (`server`, `myproject`) работает потому, что compose проекта раздаёт
  алиасы сервисов, а `nginx` подключён к его сети. Убрать сеть — сломать апстрим.
- **`root` в конфиге обязан совпадать с путём внутри php-fpm.**
  `SCRIPT_FILENAME` разворачивает php-fpm, а не nginx.
- **Монтируется только `public/` проекта**, не репозиторий целиком: иначе
  `.env` проектов оказываются внутри интернет-контейнера.
- **Нельзя запускать два postgres на одном томе.** Разные контейнеры не видят
  PID друг друга, и защита через `postmaster.pid` не срабатывает. Перед подъёмом
  общего слоя том должен быть освобождён.
- **Мажорную версию postgres нельзя поменять правкой тега.** Формат каталога
  данных между мажорами несовместим: нужен `pg_dumpall` на старой версии,
  чистый том и восстановление. Проверять результат следует не по `n_live_tup`
  (это оценка планировщика, она врёт), а точным `count(*)` против числа строк
  в COPY-блоках дампа.
- **С 18-й версии образ postgres ждёт один том на `/var/lib/postgresql`**, а
  данные кладёт в подкаталог версии. Прежнее монтирование в
  `/var/lib/postgresql/data` приводит к отказу старта.
- **Новую сеть контейнеру `nginx` docker подключает при создании.** Если сервис
  стартовал неудачно и был лишь перезапущен, сети может не хватать —
  `up -d --force-recreate nginx`.
