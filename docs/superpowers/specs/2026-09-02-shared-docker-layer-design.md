# Общий слой Docker: ClaudeDocker

Дата: 2026-09-02

## Зачем

Точка входа всего сервера (`:80`/`:443`) живёт внутри compose-проекта
`game_world_tycoon_idle`. Контейнер `nginx` оттуда обслуживает четыре проекта,
монтирует внутрь себя чужие репозитории целиком и раздаёт TLS для всех доменов.
Погасить `game` нельзя, не уронив остальное. Конфигурация при этом размазана:
server-блоки `game` и `cross_messenger` зашиты в шаблон nginx проекта `game`,
а блоки `uzbek_queue` и `myproject` лежат в репозитории `uzbek_queue`.

Задача — развести владение: общий слой отдельно, проекты отдельно.

## Принцип разделения

Два вида compose, у каждого своя цель:

- **`docker-compose.yml` в репозитории проекта** — самодостаточный: проект
  поднимается на чистой машине, со своей базой, своим кешем и своим
  веб-сервером, порты публикует сам.
- **ClaudeDocker** — композиция под этот VPS: общий вход, общая
  инфраструктура и оверлей на каждый проект, который отключает всё, что
  предоставляет общий слой.

Образец уже есть в `cross_messenger`: базовый compose плюс оверлей под машину
(`local` / `vps`), набор выбирается через `COMPOSE_FILE` в `.env`. Разница
только в том, что оверлей под VPS переезжает из репозитория проекта сюда.

Правило владения одной строкой: **если ресурс нужен более чем одному проекту —
он описан в ClaudeDocker; если только одному — в его репозитории.**

## Состав ClaudeDocker

```
docker-compose.yml              # nginx, portainer, общие postgres и redis
.env                            # НЕ в git: домены, бинды портов, пароли
.env.example                    # шаблон с пустыми значениями
.gitignore                      # .env
nginx/templates/nginx.conf.template        # каркас: events, http, mime, ACME, include
nginx/templates/sites/*.conf.template      # по файлу на проект
projects/<имя>/docker-compose.yml          # оверлей проекта под VPS
docs/superpowers/specs/                    # этот документ
```

Репозиторий публичный, поэтому в git не попадает ничего, кроме шаблонов:
домены (они содержат адрес сервера), бинды портов и пароли — только в `.env`.
Штатный entrypoint `nginx:alpine` рендерит подкаталоги шаблонов с сохранением
относительных путей, поэтому `templates/sites/game.conf.template` становится
`/etc/nginx/sites/game.conf`, а домены подставляются из окружения через
`NGINX_ENVSUBST_FILTER`.

### Сервисы

| Сервис | Что делает | Замечания |
|---|---|---|
| `nginx` | единственная точка входа, TLS, ACME | образ `nginx:alpine` |
| `portainer` | просмотр контейнеров | том подключается `external` под нынешним именем |
| `postgres` | общая база `game` и `uzbek_queue` | том подключается `external`, данные не переезжают |
| `redis` | общий кеш и очереди | новый сервис, см. «Дефекты», п. 1 |

`adminer` не переносится — удаляется совсем.

### Сети

`nginx` подключается к `web`, `claude-net` и сети проекта `game`. Это не
косметика: конфиги проксируют на короткие имена `server` и `myproject`, а они
резолвятся только внутри сетей, где compose соответствующего проекта раздаёт
алиасы сервисов. `cm-php` и `uq-php` доступны через `web`.

### Монтирование кода

Только каталог `public` каждого проекта и строго по тому же пути, который
видит его php-fpm: `SCRIPT_FILENAME` разворачивает php-fpm, а не nginx, поэтому
`root` обязан остаться прежним (`/var/www/cm/public`, `/var/www/uq/public`).
Сейчас в интернет-контейнер смонтированы целиком репозитории `cross_messenger`
и `uzbek_queue` вместе с их `.env` — после переезда этого не будет.

### Как оверлей отключает то, что даёт общий слой

Compose не умеет удалять сервис оверлеем, поэтому в базовом файле проекта
standalone-сервисы (своя база, свой кеш, свой веб-сервер) объявляются под
профилем `standalone`, а в `.env.example` проекта стоит
`COMPOSE_PROFILES=standalone`. На чистой машине проект поднимается целиком;
на VPS профиль не включён — эти сервисы просто не создаются.

Одна тонкость: если включённый сервис объявляет `depends_on` на сервис из
выключенного профиля, compose откажется стартовать. Поэтому оверлей под VPS
переопределяет `depends_on` пустым списком у тех сервисов, чьи зависимости
предоставляет общий слой.

## Что меняется в проектах

**`game_world_tycoon_idle`** — из compose уходят `nginx`, `portainer`,
`adminer`; `postgres` уезжает в общий слой, но в репозитории остаётся свой для
запуска на отдельной машине. Из `.env` уходят `HTTP_BIND`, `HTTPS_BIND`,
`ADMINER_BIND`, `PORTAINER_BIND`, `DOMAIN`, `CM_DOMAIN`. Каталог
`nginx/templates` остаётся, но обслуживает только сам `game` в standalone-режиме.

**`uzbek_queue`** — в compose появляются свои `postgres` и `redis`; исчезает
сеть `shared` с явной привязкой к сети проекта `game`. Каталог
`deploy/nginx` удаляется: `uq.conf` и `myproject.conf` переезжают в
`nginx/templates/sites/`, адрес сервера из них уходит в переменную.

**`cross_messenger`** — `docker-compose.vps.yml` переезжает в
`ClaudeDocker/projects/cross_messenger/`; базовый файл и `local`-оверлей
остаются на месте.

**`myproject`** — в репозитории появляется публикация порта для standalone;
на VPS оверлей её снимает.

## Дефекты, найденные при разборе

Это не гипотезы — проверено на живом сервере.

1. **Redis не резолвится ни для одного проекта.** У `game` и `uzbek_queue` в
   `.env` стоит `REDIS_HOST=redis`, но сервиса `redis` нет ни в одном их
   compose: единственный контейнер redis принадлежит ClaudeService и живёт в
   сети `claude-net`, куда ни один из них не подключён. `getent hosts redis`
   внутри `uq-php` и `game-server` не возвращает ничего.
2. **`uq-worker` падает в цикле** на подключении к redis — прямое следствие
   п. 1. У `uzbek_queue` на redis настроены очереди, кеш и сессии.
3. **`migr-mysql9-test` поднят голым `docker run`** и не принадлежит ни одному
   compose-проекту.

Пункты 1 и 2 закрываются самой работой: общий `redis` появляется в ClaudeDocker,
проекты к нему подключаются. Пункт 3 — отдельной задачей после переезда.

## Порядок переезда

Простой на несколько минут допустим, поэтому без временных портов.

1. Собрать `ClaudeDocker`: compose, `.env`, шаблоны, оверлеи. Проверить
   `docker compose config` — без запуска.
2. Погасить `nginx`, `adminer`, `portainer` в `game`.
3. Поднять ClaudeDocker. Общие тома (`postgres`, `portainer`) подключены
   `external` под нынешними именами — данные остаются на месте.
4. Прогнать проверку (ниже). При провале — вернуть `game` в прежний вид:
   его файлы до этого шага не менялись.
5. Только после успешной проверки — вычистить `game`, `uzbek_queue`,
   `cross_messenger`, `myproject` и перенести переменные.
6. Обновить `docs/vps-rebuild-prompts.md` в ClaudeService: сборка на чистом
   VPS теперь начинается с ClaudeDocker.

## Проверка

- Все четыре домена отвечают по HTTPS: `game`, `cross_messenger`,
  `uzbek_queue`, `myproject`.
- Вебхук `/devbot/webhook` доходит до `claudeservice-devbot-1`: сообщение из
  Telegram по-прежнему попадает в сессию.
- `uq-worker` жив дольше минуты и не пишет ошибок redis.
- В `game` не осталось контейнеров, кроме `server`.
- `docker exec` в `nginx`: внутри нет ни одного `.env` проектов.
- Каждый проект поднимается своим compose без внешних сетей — проверяется
  через `docker compose config`, без запуска второй копии на этом же сервере.
